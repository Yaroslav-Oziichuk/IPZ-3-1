## 1. Результати аналізу прикладів з open-source проєктів

### Приклад 1. Dapper: `Dictionary<Type, DbType>` (відповідність типів CLR і `DbType`)

- **Джерело:** [`Dapper/SqlMapper.cs`](https://github.com/StackExchange/Dapper/blob/684d7d9895e8b9eff4ab898528d69bd60979c098/Dapper/SqlMapper.cs), статичне поле `typeMap` (пошук за рядком `typeMap`).
- **Контекст.** Під час створення SQL-параметрів Dapper має для кожного .NET-типу значення (`int`, `string`, `DateTime`, `Guid` тощо) визначити відповідний `DbType` ADO.NET.
- **Чому `Dictionary`.** Це відображення «ключ → значення», а пошук виконується для кожного параметра кожного запиту. `Dictionary<Type, DbType>` шукає за ключем у середньому за O(1), а `List<KeyValuePair<...>>` або масив вимагали б лінійного перебору O(n).
- **Складність.** Пошук за ключем O(1) у середньому (O(n) у гіршому випадку при масових колізіях); заповнення одноразове, під час ініціалізації.
- **Особливості.** Ключ - об'єкт `Type`; для нього достатньо стандартного порівняння, бо кожен тип у процесі представлений єдиним об'єктом `Type`. Таблиця мала й переважно читається, що добре підходить для словника.

### Приклад 2. Newtonsoft.Json: кеш контрактів `ThreadSafeStore<Type, JsonContract>`

- **Джерело:** [`DefaultContractResolver.cs`](https://github.com/JamesNK/Newtonsoft.Json/blob/7217c484e9705b5e76585c8b7fcd489c8e021c23/Src/Newtonsoft.Json/Serialization/DefaultContractResolver.cs) (поле `_contractCache`); опис ідеї `ThreadSafeStore` автором бібліотеки: [блог James Newton-King](https://james.newtonking.com/archive/2009/06/18/threadsafestore/).
- **Контекст.** Побудова `JsonContract` для типу (аналіз властивостей, атрибутів, конструкторів) виконується через рефлексію та дорога. Тому результат кешується за ключем `Type`, і повторні серіалізації цього типу беруть готовий контракт.
- **Чому словникова структура.** Потрібен швидкий пошук за ключем і операція «знайти або створити»: `ThreadSafeStore` отримує делегат-фабрику, яка викликається лише при промаху кешу. `List` тут не підходить: пошук O(n) при кожній серіалізації звів би нанівець користь від кешу.
- **Складність.** Пошук O(1) у середньому; дорогий крок (рефлексія) виконується один раз на тип.
- **Особливості.** Кеш спільний для потоків, тому звичайний `Dictionary` без синхронізації небезпечний; саме тому бібліотека обгортає сховище в окремий потокобезпечний клас. Яка саме колекція під капотом у вашій версії коду (`Dictionary` із блокуванням чи `ConcurrentDictionary`), дивіться у файлі `ThreadSafeStore.cs` у репозиторії.

### Приклад 3. `HashSet<string>` (разом із `Dictionary`): набір імен властивостей, які треба ігнорувати

- **Джерело:** GitHub Gist: [ContractResolver для Newtonsoft.Json](https://gist.github.com/arman-hpp/433c8483d8d1596bf5679321c1e908e8), у якому для кожного типу зберігається `HashSet<string>` імен властивостей (структура `Dictionary<Type, HashSet<string>>`).
- **Контекст.** Під час серіалізації для кожної властивості потрібно швидко відповісти на запитання: чи входить її ім'я до списку ігнорованих для цього типу.
- **Чому `HashSet`, а не `List`.** Нам потрібні лише унікальність і перевірка належності, порядок не важливий. `Contains` у `HashSet` працює за O(1) (у `List` - O(n)), а повторне додавання того самого імені безпечне й нічого не дублює.
- **Складність.** `Add`, `Remove`, `Contains` - O(1) у середньому.
- **Особливості.** Імена властивостей порівнюються як рядки, тому доцільно явно вказувати `StringComparer` (регістр має значення для JSON).

### Контрприклад: коли `HashSet` не потрібен

У [`DefaultContractResolver.cs`](https://github.com/JamesNK/Newtonsoft.Json/blob/7217c484e9705b5e76585c8b7fcd489c8e021c23/Src/Newtonsoft.Json/Serialization/DefaultContractResolver.cs) невеликий фіксований перелік імен типів (`BlacklistedTypeNames`) зберігається у масиві `string[]`, і перевірка виконується через `Array.IndexOf`. Для кількох елементів лінійний перебір не гірший за хешування, а масив простіший і не витрачає пам'ять на хеш-таблицю. Тож «O(1) краще за O(n)» працює не завжди: для дуже малих сталих наборів накладні витрати на хешування можуть бути порівнянні з перебором.

## 2. Порівняльна таблиця

| Операція | `List<T>` | `Dictionary<TKey,TValue>` | `HashSet<T>` | Коли використовувати |
|---|---|---|---|---|
| Додавання | O(1) амортизовано (у кінець); O(n) у середину | O(1) в середньому | O(1) в середньому | усі три добре додають; `List` зберігає порядок і дублікати |
| Пошук за значенням | O(n) | O(n) (`ContainsValue`; не призначений для цього) | O(1) в середньому (`Contains`) | `HashSet`, якщо потрібна лише наявність значення |
| Пошук за ключем | N/A (лише за індексом, O(1)) | O(1) в середньому | N/A | `Dictionary`, якщо значення потрібно знаходити за ідентифікатором |
| Видалення | O(n) | O(1) в середньому | O(1) в середньому | `Dictionary`/`HashSet` для частих видалень |
| Перевірка наявності | O(n) (`Contains`) | O(1) в середньому (`ContainsKey`) | O(1) в середньому (`Contains`) | `HashSet` або `Dictionary`, якщо перевірок багато |

Додатково: O(1) для хеш-колекцій справедливо «в середньому»; у гіршому випадку (багато колізій через поганий `GetHashCode`) операції вироджуються до O(n). Хеш-колекції не гарантують порядок елементів.

Практичне підтвердження (з виводу програми, 2000 пошуків елемента з кінця колекції):

| Елементів | `List.Contains` | `HashSet.Contains` |
|---:|---:|---:|
| 1 000 | ≈ 0.8 мс | ≈ 0.06 мс |
| 10 000 | ≈ 2.9 мс | ≈ 0.06 мс |
| 50 000 | ≈ 13.8 мс | ≈ 0.06 мс |

Час `List` зростає разом із розміром колекції, час `HashSet` практично не змінюється.

## 3. Висновки про вибір колекції

**Коли `Dictionary` краще за `List`.** Коли дані треба знаходити за ключем (ідентифікатор, ім'я файлу, тип): `Dictionary` дає O(1) замість O(n). Типові ролі: кеші, довідники, індекси, лічильники.

**Коли `HashSet` оптимальний.** Коли важлива унікальність елементів і швидка перевірка «є / немає», а також теоретико-множинні операції (`UnionWith`, `IntersectWith`, `ExceptWith`): унікальні теги, відвідані вершини графа, дозволені значення, відфільтровані дублікати.

**Підводні камені.**

1. **Порівняння.** За замовчуванням рядки порівнюються з урахуванням регістру, а власні класи - за посиланням. Для потрібної семантики використовують `StringComparer.OrdinalIgnoreCase` або власний `IEqualityComparer<T>`.
2. **Узгодженість `Equals` і `GetHashCode`.** Якщо рівні об'єкти мають різні хеші, колекція працює некоректно (дублікати, «втрачені» ключі). Порушення цього контракту дає хибні результати, а погана хеш-функція ще й руйнує продуктивність.
3. **Змінювані ключі.** Якщо після додавання змінити поле, від якого залежить хеш, елемент стає недосяжним у колекції.
4. **Порядок і потокобезпека.** `Dictionary` і `HashSet` не гарантують порядок перебору й не є потокобезпечними (для багатопотокового доступу потрібні блокування або `ConcurrentDictionary`).
5. **Витік внутрішнього стану.** Повернення внутрішнього `HashSet` назовні дозволяє зіпсувати індекс; тому в реалізації повертаються копії.
6. **Мала кількість елементів.** Для 3-5 елементів масив або `List` можуть бути простішими й не повільнішими (див. контрприклад вище).

## 4. Приклади з власного коду

Реалізовано всі три сценарії (третій - додатковий).

- `FileMetadataCache`: `Dictionary<string, FileMetadata>` із `StringComparer.OrdinalIgnoreCase`, методи `Add`, `AddOrUpdate`, `Get`, `Remove`, `Contains`.
- `TagManager`: `Dictionary<string, HashSet<string>>`; `GetAllUniqueTags` (`UnionWith`), `FindCommonTags` (`IntersectWith`), `FindTagsOnlyInFirst` (`ExceptWith`).
- `SearchIndex`: `Dictionary<string, HashSet<int>>`; `SearchMultiple` через `IntersectWith`.

Фрагмент виводу:

```text
Contains("PHOTO.JPG")   = True  <- регістронезалежний ключ
Add("REPORT.PDF") повторно -> False (дублікат не додано, Count = 3)
FindCommonTags(article-1, article-2)   [IntersectWith]: {csharp, dotnet}
FindTagsOnlyInFirst(article-1, art-2)  [ExceptWith]:    {collections, linq}
SearchMultiple("c#", "java")    -> {3}
```
